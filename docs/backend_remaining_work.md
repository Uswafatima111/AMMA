## Executive summary

The previous November 27 audit is materially out of date for backend implementation. Five local commits added deterministic risk-engine validation and tests, richer static maternal-health retrieval, patient-to-mother identity compatibility, health-record access rules, emergency/referral workflows, and appointment/reminder workflows. ## A. Completed backend functionality

These items are present at current HEAD and must not be reported as missing:

- **Identity and mother profiles:** stable Firestore mother document IDs, optional `patientUid`, ASHA assignment queries, patient-link resolution, guarded legacy UID lookups, and compatibility aliases for `pregnancyWeek`/`gestationalWeeks` are implemented in `FirestoreService`. The identity behavior and ambiguous legacy-data limits are documented in `docs/patient_mother_health_record_identity.md`.
- **Health records:** assigned ASHAs can create immutable records keyed by `motherId`; create rules validate authorship, assignment, timestamps, and core measurement types. Patient/ASHA streams use mother-scoped queries, with a limited patient legacy `userId == auth.uid` fallback when no mother can be resolved. A new test file covers identity and health-record service helper behavior.
- **Risk assessment:** `RiskEngine` is deterministic, has input validation and structured outcomes, and is covered by `test/risk_engine_test.dart`. `AiRiskService` fetches the newest available record across `motherId` and legacy `userId` queries, then calls the local engine. Risk assessment remains client-side; it is not a Cloud Function or clinically validated instrument.
- **Maternal knowledge retrieval:** the static corpus and lexical retriever were expanded with relevance scoring, limits, deterministic ordering, and answer/source formatting. This is local retrieval over bundled content, not a remote LLM, embeddings pipeline, or server integration.
- **Emergency lifecycle:** `emergency_requests` has patient-create/own-read and assigned-ASHA read/status rules; the service supports `active -> responded -> resolved` and retains responder/resolution metadata. It resolves a linked or legacy mother and follows the current ASHA assignment for authorization. The service documents and enforces a 10-assigned-mother query ceiling.
- **Referrals:** new model/service and rules implement ASHA-created referrals with `pending -> accepted/cancelled` and `accepted -> completed/cancelled` transitions. Facility is stored as text; no external facility booking is provided.
- **Appointments:** service/model/rules support ASHA mother-scoped appointments and patient-owned legacy pending appointments, future dates, allowed types, status transitions, immutable appointment identity, and history-preserving cancellation in place of deletion. Patient dashboard reads use the linked mother ID plus the patient's own legacy UID rows.
- **Medicine reminders:** the ASHA mother-details screen lists reminders scoped by stable `motherId` and supports creation, instruction/date/time edits, and active toggling. Service transactions and rules check the current ASHA assignment; patient reads remain restricted to their linked mother. Dates and 24-hour times are validated, and mother/creator/creation fields remain immutable. Patients can opt into device-local appointment and medicine reminders; these are not remote notifications.
- **Patient help requests:** `AlertService.createPatientHelpRequest` accepts `benefit_help` and `appointment_request`, resolves the authenticated patient's linked mother, verifies `patientUid` ownership and the mother's `assignedAshaId`, then stores a request with `userId`, stable `motherId`, `assignedAshaId`, `type`, `riskLevel: low`, `message`, `status: open`, and `createdAt`. Rules enforce ownership, assignment, type, and field constraints. Patient and ASHA alert streams query by `motherId`; rules do not treat arbitrary `userId` as authorization. Patients read alerts tied to their own mother; assigned ASHAs read alerts for mothers currently assigned to them. The patient dashboard now exposes the existing request form. These are stored requests, not notifications.
- **Firebase rules exist for** `users`, `mothers`, `health_records`, `appointments`, `medicine_reminders`, `alerts`, `emergency_requests`, and `referrals`. They default-deny unmatched collections and disallow deletion of the newly protected clinical/workflow records.
- **Automated unit tests exist** for the risk engine, patient/mother/health-record helper behavior, appointment/reminder logic, emergency/referral lifecycle helpers, and AI/retrieval behavior. These are not a substitute for Firestore Rules Emulator tests.
- **Latest security verification:** the complete isolated demo Firestore Emulator suite reports 32 passed, 0 failed, 0 cancelled. This includes health-record and alert ownership regressions plus existing workflow tests. No production data was queried or backfilled.
- **Flutter test status:** the latest known full run before this integration pass was 102 passed, 0 failed. Full-suite execution has since stalled in the test runner; it was not repeatedly relaunched during this focused pass, so current Flutter status is unverified. Four mother-registration tests use `fake_cloud_firestore` with a staged transaction wrapper and do not prove rollback against a real Firestore server.
- **Registration and reminder verification (2026-11-28):** four focused mother-registration tests passed; the ASHA reminder create/edit/deactivate widget and service tests are present. Local scheduling tests do not verify physical notification delivery on a handset.

## B. Partially implemented functionality

- **Shared mother schema:** `createMotherProfile` accepts and writes most required contract fields. Its ASHA-created data does not include `id` in Firestore Rules' validation set (the service writes it), and the rules do not enforce the contract's required fields/types/ranges. Some required fields can be blank or clinically implausible at service/rules level. `createdAt` uses a server timestamp. Existing mother records are not migrated or verified.
- **Patient identity uniqueness:** linked registrations write `users/{patientUid}.assignedMotherId` together with the mother record in a client transaction. This gives rules a direct pointer for assignment-scoped profile reads, but it does not ensure global uniqueness across ASHAs or concurrent creates; duplicate links are detected on patient lookup and fail safely. Existing generated-ID links still need a production backfill. There is no trusted backend creation endpoint.
- **Health-record contract:** contract fields are supported, but `riskLevel`, `matchedRules`, `explanation`, `recommendation`, and `ruleVersion` are optional in the service/rules even though `shared_contract.md` lists them as health-record fields. Legacy `userId`/`recordedAt` compatibility is partial by design. No explicit migration/backfill is implemented.
- **Health-record ownership hardening:** new records require an assigned, existing `motherId`; an optional `userId` must match that mother's linked patient (or the legacy UID-keyed mother ID). Patient reads of canonical records require the verified mother relationship and a matching optional `userId`. The legacy fallback is limited to userId-only records for patients with no `assignedMotherId` and no UID-keyed mother record. Emulator coverage now includes forged/mismatched IDs, missing/invalid mother ownership, the legacy fallback, and unassigned ASHA denial.
- **Appointment compatibility:** stable mother-ID records work; old ASHA appointments containing only `userId` cannot be safely queried as assigned-mother records and are deliberately not backfilled. Patient reads use the linked mother ID plus their own legacy UID scope. Old ASHA records need an approved migration or trusted read path.
- **Emergency routing:** linked patient profiles cannot omit their mother pointer to write an unassigned request, and the pointer cannot be cleared by the patient. The UID-keyed legacy mother path is also checked for patient identity. Generated-ID legacy records lacking `assignedMotherId` still require production backfill because Rules cannot query for their absence. A request is not an ambulance dispatch, phone call, push notification, or guaranteed delivery to an ASHA.
- **Alerts:** patient help requests and ASHA mother alerts can be created and read through scoped queries. Assigned ASHAs can acknowledge and advance patient requests through the defined statuses; patients cannot update them. Alert deletion remains denied. No remote or local alert notification delivery exists; creating or updating an alert does not mean it was delivered to or seen by an ASHA.
- **ASHA contact:** `AshaService.getAshaContact` resolves the patient's verified mother link and reads only the assigned ASHA's allowlisted contact projection. Emulator tests cover authorized contact access and denial of unrelated/sensitive profile fields. Generated-ID links without a matching `assignedMotherId` still require production backfill.
- **Authentication:** email/password sign-in and trusted-profile role lookup are implemented. Patient profile self-creation is allowed by rules; ASHA provisioning is expected to be administrative, but no provisioning workflow or documented admin bootstrap is included. The profile update rule preserves role/id but does not constrain other changed fields.
- **Frontend integration:** ASHA reminder controls and patient-local reminders are connected. The patient dashboard now includes stored help-request creation and assigned-ASHA contact lookup; ASHA login attempts to publish the caller's allowlisted contact projection. ASHA mother-detail health-record, appointment, alert, and reminder reads use the stable mother ID and tolerate legacy field aliases. Appointment/referral/health-record creation and editing forms are not all present; Tahoor should connect or confirm those intended frontend entry points rather than treating service APIs as UI-complete.

## D. Firestore security and schema problems

### Authorization and query mismatches

- **Alert query scopes:** `AlertService.getAlerts` resolves the authenticated patient's linked mother and filters by stable `motherId`; `watchAlertsForMother` also uses `motherId`. Neither uses a collection-wide read or grants access through an arbitrary `userId`. Emulator tests cover patient-owned request queries and assigned-ASHA mother queries.
- **Alert status mutations:** `markAsRead` and `updateAlertStatus` support only the defined patient-request transitions for the mother’s currently assigned ASHA and update `status` only. The immutable `assignedAshaId` remains a creation-time snapshot across reassignment. Patient updates, unrelated-ASHA updates, immutable-field changes, invalid transitions, and all deletes are denied. The patient dashboard displays requests without attempting a patient-side acknowledgement; the assigned ASHA remains responsible for status changes. The legacy generic `createAlert` payload may still be rejected when it lacks current ASHA mother-scoped fields; use the supported ASHA mother writer or patient help-request writer.
- **Mother mutation mismatch:** legacy `FirestoreService.updateMother` and `deleteMother` write directly without checking caller/assignment; rules deny ASHA updates and all deletes, so these methods fail. There is no authorized ASHA profile-edit or reassignment path. This also prevents the documented reassignment lifecycle from being exercised through an implemented mother service.
- **Health-record mutation mismatch:** `deleteHealthRecord` is exposed but rules prohibit deletion. `getHealthRecord` performs a direct client read and relies on rules; ambiguous legacy rows that do not fit the documented userId-only fallback need reviewed migration.
- **Health-record legacy compatibility:** patient access through `userId` alone is intentionally limited to records with no `motherId` and no resolvable mother link. Canonical records with a mismatched `userId` are denied to patients even when they own the mother; the assigned ASHA can still read them for remediation. Review existing malformed rows before rollout.
- **Patient access to ASHA contact:** patient contact lookup reads only the assigned ASHA's allowlisted `asha_contacts/{ashaUid}` projection, after resolving the verified mother relationship. The patient dashboard displays this contact; ASHA login publishes the projection. Missing phone details remain unavailable, and generated-ID patient links lacking `assignedMotherId` still need backfill.
- **User profile field validation:** users may self-create a patient profile with arbitrary additional fields; updates can change any non-role/non-id field. Restrict allowed keys/types and updateable fields, especially if phone/contact information is used for lookups.
- **Mother schema validation gaps:** rules validate assigned ASHA and optional patient role but do not validate required contract keys/types, `riskLevel` enum, timestamps, or sensible bounds. Patient updates are restricted to contact fields, but the rule's diff key check should also enforce exact types and a stable `patientUid` field shape. ASHA create is allowed to omit almost all required contract fields.
- **Legacy rules are inconsistent:** `appointmentMotherId` treats an old `userId` as a mother ID for ASHA update authorization, but query/read support for legacy userId-only appointment records is explicitly limited. Compatibility conditions need to be tested against actual query shapes and records rather than assumed equivalent.
- **Emergency orphan rule gap:** a patient with a current `assignedMotherId` or UID-keyed legacy mother cannot omit the relationship or clear the pointer. Historical generated-ID links missing `assignedMotherId` remain undetectable by Firestore Rules because rules cannot query the `mothers` collection for absence; backfill those records or route creation through a trusted service.
- **Request/document schema gaps:** emergency create does not require an exact document ID field or constrain optional coordinate types/ranges. Referral create does not validate an ID field/document ID relationship and does not bound/trim facility text. Appointment and alert rules also have incomplete field validation (for example optional doctor/facility/notes bounds and exact permitted keys are not uniform on patient create).
- **Collection contract drift:** `emergency_requests`, `referrals`, and `medicine_reminders` are additional collections outside the five primary shared-contract collections and have separate notes, which is reasonable, but the canonical shared contract has not been updated to include their schema/lifecycle. Alerts and emergency requests currently represent different workflows and need explicit integration semantics.

### Schema/integrity and data exposure

- Stable `motherId` is canonical for linked health records. `AiRiskService.assessLatestRecord` resolves the authenticated patient's link when called with the legacy `userId` API and uses a mother-scoped query; the `userId` fallback is limited to an authenticated, genuinely unlinked patient. Firestore rules remain the authorization boundary for explicit `motherId` calls.
- Service-side validation is not a security boundary. Any client can write directly through Firebase SDK, so required types, allowed keys, immutable fields, and relationships must be enforced in rules or a trusted backend.
- Existing documentation states rules are local/not deployed; no Firebase deployment verification is present. Treat the checked-in rules as source intent, not proof of production authorization.
- `firestore.indexes.json` declares the composite `emergency_requests` index for the assigned-mother `whereIn` plus unresolved-status query and is referenced by `firebase.json`. Emulator tests do not establish that the index is deployed or available in the production project.

## E. Bugs and integration risks

- **Contract callers may hit permission-denied errors** for alert delete, mother update/delete, and health-record delete, because callable service methods exceed the current rules.
- **Alert delivery remains incomplete:** help requests are stored, readable by the patient and assigned ASHA, and manageable through status transitions by the assigned ASHA. Notifications are not implemented; do not represent these records as delivered or acted upon.
- **Reassignment is underspecified in code:** lifecycle authorization follows a mother's current `assignedAshaId`, but no supported ASHA/admin reassignment method or authorization policy exists. Direct privileged console changes may work, but are not a backend workflow or tested operational process.
- **Patient profile assignment pointer:** the broad ASHA profile-read grant has been removed. Assigned ASHA access now depends on `assignedMotherId` matching a mother record that confirms the patient and current ASHA. Existing generated-ID links may lack this field and need a production backfill; that backfill is not complete or verified.
- **Legacy query compatibility:** appointment, health-record, and reminder callers should continue using the scoped service methods. Old userId-only ASHA records cannot safely be exposed through the canonical mother-scoped queries until reviewed and migrated.
- **Duplicate-link race:** two ASHAs can create profiles linked to one patient concurrently. Current per-ASHA scan does not prevent it; lookup fails if duplicates are found, but does not resolve them.
- **Emergency caseload cap:** ASHA request aggregation explicitly fails above 10 assigned mothers. This is safe and documented but operationally limits scale until the API/query design changes.
- **Clinical signal limits:** the engine is tested as deterministic code, but test coverage does not validate clinical appropriateness. No clinical citations/review record or production safety validation was found.
- **RAG source quality and updates:** retrieval is local/static. Traceable source versions, reviewers, source update process, multilingual coverage, and response evaluation are not established by the current repo evidence.
- **Firebase configuration scope:** `firebase.json` configures the Firestore Emulator on port 8080, points to checked-in rules and indexes, and retains the starter Functions codebase. `functions/index.js` contains no business functions. Android's current package ID is `com.example.amma`; this checkout has no `android/app/google-services.json`, and `lib/firebase_options.dart` contains web configuration only. Android Firebase registration/native options and a device build remain release blockers; the correct registered Android app credentials must be supplied rather than guessed. Android release signing also needs project-owned production configuration.
- **Frontend integration:** this pass connected the patient help-request and assigned-ASHA contact cards, ASHA contact publication on login, and stable mother-ID reads in ASHA mother details. Patient/ASHA appointment, referral, and health-record create/edit entry points are not comprehensively present or device-tested; confirm which belong in Tahoor's UI integration. Risk dashboard presentation and error behavior also need an integration run.
